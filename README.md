# FeedFlow — 배합사료 유통 관리 플랫폼 (WMS)

전국 5개 물류 거점의 재고를 **로트(Lot) 단위로 추적**하는 창고 관리 시스템입니다.
유통기한이 있는 사료를 다루기 때문에 "재고가 몇 개인가" 만으로는 부족하고,
**어느 로트가 어느 구역에 얼마나 있고 언제 만료되는지**를 항상 알 수 있어야 합니다.

> 이 저장소는 **관리자 시스템(WMS) 모듈**입니다. 고객 주문 화면은 팀원이 담당합니다.
> `Product.imageUrl` · `description` 처럼 쇼핑몰 전용 컬럼은 엔티티에는 두되
> 관리자 화면에는 노출하지 않습니다.
>
> **농장 고객사(`farmCustomers`)는 팀원 모듈에서 옮겨온 것**입니다. 옮기면서 담당 창고를
> `centers` 참조로, 축종을 `AnimalType` enum 으로 바꾸고 거리를 우리 좌표 기준으로
> 다시 계산했습니다. 두 프로젝트를 실제로 합치기 전에 정해야 할 것은
> [`INTEGRATION-NOTES.md`](INTEGRATION-NOTES.md) 에 정리해 두었습니다.

## 실행

```bash
cd feedflow
./gradlew bootRun        # Windows: gradlew.bat bootRun
```

`http://localhost:8080` 접속. **별도 DB 설치나 API 키 발급이 필요 없습니다.**
H2 인메모리 + `data.sql` 시드가 자동으로 올라오고, 지도도 API 키 없이 바로 뜹니다.

| 계정 | 비밀번호 | 권한 |
|---|---|---|
| `admin@feedflow.co.kr` | `admin123` | ADMIN (책임자) — 매출 · 사원 관리 · 폐기 · 출고 취소 |
| `staff@feedflow.co.kr` | `staff123` | STAFF (사원) — 재고 · 입출고 · 도면 |

H2 콘솔은 `/h2-console` (JDBC URL `jdbc:h2:mem:feedflow`, 사용자 `sa`, 비밀번호 없음).

## 핵심 아키텍처 — 단일 창고에서 전국망으로

이 프로젝트의 뼈대는 **한 번에 설계된 것이 아니라 5단계로 확장된 것**입니다.
각 단계에서 "지금 구조로는 표현할 수 없는 것"이 무엇인지 찾고 그것만 바꿨습니다.

```
[WMS 1.0]  단일 물류센터 안의 건물 2동
           Warehouse enum(WH1 · WH2) — 값을 추가하려면 코드를 다시 배포해야 한다
                │
     P1 ────────┤  enum → centers 테이블로 승격
                │  전국 단위에서는 센터가 운영 중에 늘고 줄어든다
                │
     P2 ────────┤  재고 · 이력 조회에 센터 축 추가
                │  "이 센터의 재고" 를 물어볼 수 있게 된다
                │
     P3a ───────┤  센터 간 이관 (TRANSFER_OUT / TRANSFER_IN)
                │  MOVE 로 처리하면 3계층 불변식이 깨진다  ← 어필 포인트 ①
                │
     P4a ───────┤  전국 5거점 시드 + 물류망 대시보드
                │  센터별 분포 · 실적 · 경보를 한 화면에서 비교
                │
     P4c ───────┤  전국 거점 지도 + 2D 도면 양방향 연동  ← 어필 포인트 ③
                │
     P5 ────────┘  팀원 고객 농장 모듈 통합 + 수요 계획
                   농장의 축종과 품목의 축종을 같은 enum 으로 통일하니
                   "담당 농장 수요 vs 센터 재고" 를 축종별로 대조할 수 있게 된다
```

전 단계에서 지킨 **재고 3계층 불변식**이 이 확장의 기준선입니다.

```
Product.totalStock  =  Σ ProductLot.lotQuantity  =  Σ Inventory.quantity
   (품목 장부)              (로트별 잔여)              (구역별 실물)
```

`Product.totalStock` 은 **전국 합계로 유지**합니다. B2C 쇼핑몰이 이 컬럼을
'판매 가능 수량' 으로 읽고 있어 센터별로 쪼개면 연동이 깨집니다.
센터별 수량은 비정규화 컬럼을 추가하는 대신 집계 쿼리로 구합니다.

상세 설계 근거: [`docs/architecture-notes.md`](docs/architecture-notes.md) ·
[`docs/requirements.md`](docs/requirements.md) · [`docs/erd.md`](docs/erd.md) ·
[`docs/epic-p3-design.md`](docs/epic-p3-design.md) ·
[**`docs/retrospective.md`**](docs/retrospective.md)

## 어필 포인트 ① 데이터 정합성 방어 — `IN_TRANSIT` 가상 구역

**문제.** 센터 간 재고 이동을 기존 `MOVE` 유형으로 처리하면 정합성이 깨집니다.
`MOVE` 는 총량이 변하지 않는다는 전제(`sign = 0`)로 만들어졌지만,
센터가 다르면 **출발 센터의 재고는 실제로 줄어듭니다.**

더 근본적인 문제는 **"운송 중인 재고는 어디에 속하는가"** 입니다.
출발 센터에서 빼고 도착 센터에 넣기 전, 그 재고를 어디에도 두지 않으면
3계층 불변식이 깨지고 `/admin/inventory/sync` 정합성 점검이 오탐합니다.

**선택지와 판단.**

| 안 | 방식 | 판단 |
|---|---|---|
| A | 별도 전표 테이블에만 수량을 둔다 | ❌ 운송 중에 불변식이 깨져 점검 로직에 예외를 넣어야 한다. **그 예외가 진짜 어긋남을 가려버린다** |
| B | **출발 센터 소속 `IN_TRANSIT` 가상 구역을 경유** | ✅ 채택 |
| C | 전표 엔티티 + 관리 화면 전체 구현 | ❌ 포트폴리오 범위 초과 (P3b 로 유예) |

> 안전 장치를 추가하려고 기존 안전 장치를 무디게 하는 거래는 하지 않았습니다.

**구현.**

```
같은 센터 : MOVE 1건                        (sign 0, 총량 불변)
다른 센터 : TRANSFER_OUT + TRANSFER_IN 2건   (-1 / +1, 합 0)
            └ 출발 센터 소속 IN_TRANSIT 가상 구역을 경유
```

가상 구역을 **출발 센터 소속**으로 둔 이유는 운송 중 재고가 아직 출발 센터의
책임 아래 있고, 분실·파손 시 책임 소재도 그쪽이기 때문입니다.

**부수 효과 — `BinPurpose` 의 축을 셋으로 나눴습니다.**
작업 중 "대기 구역"과 "운송 중"이 성격이 전혀 다르다는 것을 알게 됐습니다.
둘 다 적재율 통계에서 빠지지만, 대기 구역은 **창고 안의 실제 바닥**이라
한도가 있고 도면에 그려야 합니다. 운송 중은 물리적 공간이 아닙니다.

| 축 | 묻는 것 |
|---|---|
| `countedInCapacity` | 적재율 통계에 포함하는가 |
| `physicalSpace` | 실재하는 바닥인가 (한도 검증 · 도면 표시) |
| `systemManaged` | 시스템이 만드는 구역인가 (사람이 고를 수 없다) |

적재 한도는 `maxCapacity` 를 큰 수로 잡아 우회하지 않고 **검증 자체를 건너뜁니다.**
임의의 큰 수는 언젠가 넘고, 넘었을 때 왜 막혔는지 알 수 없습니다.

**감출수록 관찰할 수 없게 된다는 문제도 함께 다뤘습니다.**
가상 구역을 모든 화면에서 숨기면 이관이 중간에 깨져도 알아챌 방법이 없습니다.
이관은 한 트랜잭션에서 끝나므로 잔량은 항상 0 이어야 하고, 정합성 점검 화면에
**잔류 재고 항목**을 따로 두어 0 이 아닐 때만 드러나게 했습니다.

## 어필 포인트 ② 도메인 최적화 — 적재율의 분자와 분모

**문제.** 센터 적재율이 이렇게 계산되고 있었습니다.

```
적재율 = 센터의 전체 재고 / 보관 구역 수용량
```

분모는 활성 **보관** 구역만 셉니다. 그런데 분자는 입고 대기 · 출고 대기 ·
운송 중 · 사용 중지 구역까지 **모두** 셌습니다.
시드에 대기 구역 재고가 없어 두 값이 우연히 같았고, 화면에서는 아무 문제도
드러나지 않았습니다.

**입고 등록으로 대기 구역에 물건이 들어오는 순간** 어긋납니다.
같은 센터가 2D 도면에서는 60%, 대시보드에서는 90% 로 보입니다.
도면은 대기분을 적재율에서 빼고 `+ 대기 구역 N포대 별도` 로 따로 표시하기 때문입니다.
심하면 적재율이 100% 를 넘습니다.

가장 뜨끔했던 것은 `findStorageCapacityByCenter()` 주석에 이미 이렇게 적어 뒀다는 점입니다.

> 기준이 도면과 다르면 같은 센터의 적재율이 화면마다 다르게 보인다.

**분모만 그 기준을 지키고 분자는 지키지 않았습니다.**

**해결.** 두 값을 나눠 각자의 쓰임에 맞게 씁니다.

| 값 | 쿼리 | 쓰임 |
|---|---|---|
| 전체 재고 | `findStockByCenter()` | **분포 · 비중** — 대기 구역 물건도 그 센터에 실물로 있고, 운송 중 재고도 출발 센터로 잡아야 전국 합계가 맞는다 |
| 보관 구역 재고 | `findStorageStockByCenter()` | **적재율 · 남은 여유 · 적재 상태 뱃지** — 분모와 기준이 같다 |

차이(`전체 − 보관`)는 숨기지 않고 `waitingQuantity` 로 표시합니다.
그러지 않으면 "재고 900 인데 적재율은 60%" 를 설명할 수 없습니다.

**그리고 라벨이 계산을 반박하고 있었습니다.**

```
전국 보관 수량   4,836 / 수용 9,600 포대
전국 적재율      48%
```

숫자는 전부 맞습니다. 4,836 은 전체 재고이고 적재율의 분자는 보관 구역 재고
4,570 입니다(4,570 ÷ 9,600 = 48%). 문제는 라벨이 **'보관' 이라는 단어를 전체
재고에 붙여** 바로 옆의 계산을 반박한다는 것이었습니다.
심사관이 "왜 50% 가 아닌가" 라고 물으면 화면만으로는 답할 수 없습니다.

- `전국 보관 수량` → **`전국 재고 수량`**
- 부제에 `보관 4,510 / 수용 9,600 포대` 를 넣어 **적재율의 분자를 그 자리에 노출**
- 분포 도넛 부제: `보관 수량 기준` → `대기 · 운송 중 포함` (기준이 다름을 명시)

**재발 방지.** 적재율 계산을 `usageRate(storageQuantity, storageCapacity)` 헬퍼로
모으고, 변수명을 `s` / `ss` 에서 `totalStock` / `storageStock` 으로 바꿨습니다.
**한 글자 차이인 이름이 이 버그의 원인이었습니다.**

## 어필 포인트 ③ UX · 시각화 — 양방향 지도와 시계열 밸런싱

### 지도 라이브러리를 Leaflet + OSM 으로 고른 이유

카카오맵 · 네이버지도를 쓰지 않았습니다. **앱 키 발급과 도메인 등록 없이는
지도가 아예 뜨지 않기 때문**입니다. 이 저장소를 클론해서 실행하는 사람이
키를 설정하지 않으면 빈 회색 박스를 봅니다.
Leaflet(BSD-2) + OSM 타일은 **키 없이 즉시 동작**하고 마커 · 팝업 · 이동
애니메이션이 모두 있어 양방향 연동에 필요한 것이 다 있습니다.

교체 지점은 `createMap` / `addPin` / `focusPin` **세 함수로 국소화**하고
주석에 적어 뒀습니다. 카카오맵으로 바꿀 때 고칠 곳이 세 군데뿐입니다.

### 양방향 연동은 방향에 따라 처리가 다릅니다

| 방향 | 처리 | 이유 |
|---|---|---|
| 지도 핀 → 2D 도면 | 페이지 이동 (`?centerId=`) | 도면은 서버 렌더링이다. 구역 좌표 · 적재율 집계를 모두 서버가 계산하므로 센터가 바뀌면 다시 받아야 한다 |
| 2D 도면 탭 → 지도 | 같은 센터면 `preventDefault()` 후 **지도만** 이동 | 클라이언트에 이미 모든 핀이 있다. 매번 페이지를 다시 받으면 지도가 처음부터 로드되며 깜빡인다 |
| 탭 hover | 핀만 강조 (이동 없음) | 마우스가 지나가기만 해도 지도가 움직이면 어지럽다 |

### 좌표를 `Center` 컬럼으로 둔 이유 (프론트엔드 Geocoder 거부)

- 좌표는 파생값이 아니라 센터가 가진 **기준 정보**입니다.
- 변환 API 는 키와 호출 한도가 있고, **실패하면 핀이 하나도 찍히지 않습니다.**
- 기획 단계 주소는 `"고덕면 몽곡리 667 일대"` 처럼 **범위**로 적혀 있어
  변환 결과가 호출 시점마다 달라질 수 있습니다. 핀이 조금씩 움직이는 지도가 됩니다.

좌표는 `nullable` 입니다. 부지 확정 전에 센터를 먼저 만들어 재고를 배분하는 일이
실제로 생기기 때문입니다. 좌표가 없으면 **지도에서만 빠지고** 도면 · 재고 · 이관은
그대로 동작하며, 대신 `missingCount` 로 **몇 곳이 빠졌는지 화면에 알립니다.**
조용히 빼면 핀 수가 센터 수와 달라도 아무도 눈치채지 못합니다.

> 지도는 **보조 정보**입니다. HTML 에 좌표를 심지 않고
> `GET /api/admin/center-pins` 를 `fetch` 로 가져오며, CDN 이나 타일 서버가
> 죽어도 2D 도면 본문은 그대로 보이도록 모든 실패를 안내 문구로만 표시합니다.

### 시드 데이터도 '보여줄 수 있는가' 를 기준으로 검증합니다

정합성 규칙을 다 지켜도 **기능을 보여주지 못하는 데이터**가 만들어집니다.

| 증상 | 규칙 위반 | 화면에서 보이는 것 |
|---|---|---|
| 최근 7일 입고 +1,660 / 출고 −10 | 없음 | "물류가 멈춘 창고" |
| 활성 보관 구역인데 재고 0 | 없음 | 2D 도면의 영구 빈 칸 |
| 시드부터 포화(90%↑)인 구역 6곳 | 없음 | 포화 경보가 의미를 잃고, 이동을 시연할 여유도 없다 |
| 대기 구역 재고가 0 | 없음 | `+ 대기 구역 N포대 별도` UI 가 **한 번도 렌더링되지 않는다** |

**출고 이력 보강 방식** — `SHIPPED` · `DELIVERED` 주문 10건 전부에 `OUTBOUND` 를
붙이면 최종 재고가 줄어듭니다. 그래서 짝이 되는 `INBOUND` 를
**25일 더 오래된 날짜**로 함께 넣었습니다.

```
입고 +q (25일 이상 과거)  +  출고 −q (주문일)  =  0
```

기간 집계(최근 7일)는 움직이는데 최종 재고 배치는 그대로입니다.
결과: 최근 7일 **입고 +430 / 출고 −180 · 폐기 −15**.

이력 누적 = 최종 재고를 로트 단위뿐 아니라 **`로트 × 구역` 단위까지** 맞췄습니다.
`MOVE` · `TRANSFER` 의 출발 구역에 그 로트가 입고된 기록이 없으면 로트 총량은
맞아도 구역별로는 어긋나고, 이력 추적 화면이 정합성 경고를 띄웁니다.

## 재고 이력 유형

| 유형 | sign | 설명 |
|---|---|---|
| `INBOUND` | +1 | 입고 |
| `OUTBOUND` | −1 | 출고 (FEFO, `orderId` 를 남겨 취소 근거로 쓴다) |
| `CANCEL` | +1 | 출고 취소 복구 (입고와 구분 — 매입 실적에 섞이면 안 된다) |
| `DISPOSAL` | −1 | 폐기 |
| `MOVE` | 0 | 같은 센터 안 구역 이동 |
| `TRANSFER_OUT` / `TRANSFER_IN` | −1 / +1 | 센터 간 이관 (두 건의 합이 0) |
| `ADJUST` | 0 | 재고 조정 |

## 검증

### 테스트

**278개 / 22개 클래스.** 서비스 단위 테스트(Mockito)가 중심이고,
JPQL 안에만 존재하는 조건은 `@DataJpaTest` 로 실제 H2 에 데이터를 넣어 검증합니다.

- `AllocatableStockRepositoryTest` — 다섯 용도의 구역을 만들어 **보관 · 출고 대기만**
  출고 후보로 나오는지, 단건 조회와 미리보기용 일괄 조회의 조건이 같은지
- `WarehouseMapRepositoryTest` — 재고가 없는 구역도 도면에 남는지(outer join 유지)
- `DashboardAlertRepositoryTest` — 안전재고 · 유통기한 경보 집계
- `FarmCustomerRepositoryTest` — **세는 기준이 컬럼마다 다른** 집계
  (농장 수는 거래 보류 포함, 월 사료량은 거래 중만), 담당 농장이 없는 센터가
  `group by` 결과에서 빠지는지, 담당 센터가 취급하지 않는 축종 검출(`not exists`)
- `DemandPlanRepositoryTest` — 공급이 **출고 가능 구역만** 세는지(보관·출고 대기 150 vs
  전체 1,050), 수요가 **거래 중 농장만** 세는지(1,570 vs 3,950), 두 집계가 같은
  `(센터, 축종)` 축으로 나오는지

### 시드 데이터 (`data.sql`)

정합성 5규칙과 표시 품질 6항목을 함께 검증합니다.

```
1  이력 누적(Σ movement × sign)        = ProductLot.lotQuantity
2  구역 재고 합계(Σ Inventory.quantity) = ProductLot.lotQuantity
3  Product.totalStock                  = 품목별 로트 수량 합계
4  구역별 적재량                        ≤ WarehouseBin.maxCapacity
5  로트 × 구역 단위 이력 누적           = 해당 구역의 재고
```

### 정적 검사

> ⚠️ 개발 샌드박스는 외부 네트워크가 차단(`INTEGRATIONS_ONLY`)되어 Gradle
> 의존성을 받을 수 없습니다. **컴파일 · 테스트 실행은 로컬에서만 가능**하며,
> 샌드박스에서는 정적 검사로 대체했습니다.

검사 스크립트는 [`tools/`](tools/) 에 있습니다. Python 3 만 있으면 실행됩니다.

```bash
cd feedflow
python3 ../tools/static_check.py          # 정적 검사 14종
python3 ../tools/compile_risk_check.py    # 컴파일 리스크 7종
python3 ../tools/stub_check.py            # Mockito STRICT_STUBS
python3 ../tools/verify_seed.py           # 시드 정합성 5규칙 + 표시 품질
python3 ../tools/verify_farm_seed.py      # 농장 시드
```

import 누락/미사용 · 괄호 균형 · enum `switch` 망라성 ·
JPQL `select new` 인자 수 ↔ record 컴포넌트 수 · 테스트 스텁 ↔ 리포지토리 메서드 ·
템플릿 `${}` ↔ 컨트롤러 모델 키 · 템플릿 프로퍼티 ↔ DTO 게터 ·
JS 가 읽는 JSON 필드 ↔ record 컴포넌트 · `node --check` · CSS 괄호 균형 ·
**Lombok 빌더 체인 ↔ 실제 필드** · **enum 상수 참조(JPQL 문자열 안까지)** ·
**JPQL `:param` ↔ `@Param`** · 타입 해석(import · 같은 패키지 · `java.lang`)

검사기를 만들 때마다 **일부러 오류를 심어 검출되는지 확인한 뒤 원복**했습니다.
검사기가 조용히 통과만 하고 있는 것과 실제로 잡는 것은 다릅니다.

> 실제로 `compile_risk_check.py` 는 첫 실행에서 **503건을 실패로 보고했는데 전부
> 오탐**이었습니다. 빌더 체인 파싱에서 괄호 깊이를 세지 않아 인자 안의 메서드 호출을
> 빌더 메서드로 오인한 것입니다. 그 결과를 믿었다면 정상 코드를 잘못 고쳤을 것입니다.
> 과정은 [`docs/retrospective.md`](docs/retrospective.md) 6장에 적었습니다.

## 의도적으로 만들지 않은 것

| 항목 | 이유 |
|---|---|
| B2C 쇼핑몰 | 팀원 담당. DB 만 공유 |
| 반품 절차 | 배송 완료 주문은 취소 대상이 아니다. 실물이 고객에게 있어 창고 재고를 되돌리면 실물과 장부가 어긋난다 |
| 이관 전표 엔티티 (P3b) | 두 구간이 이미 분리되어 있어 나중에 두 번째를 즉시 호출하지 않으면 된다. 구조를 다시 짜지 않는다 |
| 스마트 주문 할당 (P4b) | 농장 고객사를 통합해 **좌표 · 거리 · 축종 · 담당 센터가 갖춰졌다.** 남은 것은 주문 시점에 어느 센터에서 낼지 고르는 규칙이다. 최단 거리 센터가 그 축종을 취급하지 않을 수 있어(나주는 가금 전용) 거리만으로 정할 수 없고, 그 경우를 `/admin/farm-customers` 가 경고로 보여준다 |
| 재고 실사 | `ADJUST` 유형만 정의되어 있고 실물 카운트 입력 절차는 없다 |
