# 회고 — 기술적 난제와 극복 과정

FeedFlow 관리자 시스템(WMS)을 만들면서 실제로 막혔던 지점과, 그때 무엇을 놓고
고민했고 왜 그렇게 결정했는지를 남깁니다.

결과물의 자랑이 아니라 **판단의 기록**입니다. 그래서 채택한 안뿐 아니라
**거부한 안과 거부한 이유**를 함께 적었고, 제가 잘못 판단해서 두 번 반복한
실수도 지웠다 쓰지 않고 그대로 남겼습니다.

각 설계의 최종 형태와 화면 설명은 [`../README.md`](../README.md) 에 있습니다.
이 문서는 그 결론에 이르는 **과정**을 다룹니다.

## 1. 시드 데이터를 고치려다 찾은, 이미 도달 가능했던 치명적 버그

> **한 줄 요약** — "화면이 안 예쁘다" 는 UI 품질 문제를 파다가
> **검수를 통과하지 않은 재고가 고객에게 출고될 수 있는** 도메인 버그를 찾아
> 쿼리 단에서 막았습니다.

### 발단 — 한 번도 렌더링된 적 없는 UI

2D 도면 화면에는 P4a 단계부터 이런 표시가 있었습니다.

```
적재율 62%   (1,240 / 2,000 포대)
+ 대기 구역 180포대 별도
```

적재율 통계에서 빠지는 입고 대기 · 출고 대기 물량을 따로 알려 주는 문구입니다.
그런데 화면을 아무리 돌려 봐도 이 줄이 보이지 않았습니다.

원인은 단순했습니다. **시드의 대기 구역 재고가 전부 0** 이었습니다.
`th:if="${...hasWaitingStock}"` 조건이 걸린 UI 가 세 곳 있었고, 그 세 곳 모두
**한 번도 렌더링된 적이 없었습니다.**

여기서 이런 질문을 받았습니다.

> "대기 재고는 내가 직접 입고 등록으로 기입해서 봐야 하는 거야?"

날카로운 질문이었습니다. 심사관이 이 프로젝트를 5분 본다면
입고 등록 화면에 들어가 대기 구역을 골라 물건을 넣는 일까지 하지 않습니다.
**시연 없이 기본 데이터만으로 보이지 않는 기능은 없는 기능과 같습니다.**
그래서 시드에 대기 구역 재고를 심기로 했습니다.

### 전개 — 시드를 심으려는데 손이 멈췄다

대기 구역에 재고를 넣기 전에 확인할 것이 있었습니다.
**"이 재고는 출고 후보에서 빠지는가?"**

입고 검수를 통과하지 않은 물건이 주문 출고에 잡히면 안 됩니다.
FEFO 출고 후보를 뽑는 쿼리를 열어 봤습니다.

```java
// 당시 findAllocatableByProductId 의 조건
where p.productId = :productId
  and i.quantity > 0
  and l.expirationDate >= :today   // 만료 로트 제외 ✅
  and b.active = true              // 사용 중지 구역 제외 ✅
order by l.expirationDate asc, b.binCode asc
```

**`binPurpose` 조건이 아예 없었습니다.**

즉 구역의 용도를 전혀 보지 않고, 그 품목의 재고라면 무엇이든 출고 후보로
집어 올리고 있었습니다. 여기에 걸리는 것은 두 가지입니다.

| 대상 | 실제 상태 | 출고되면 |
|---|---|---|
| `RECEIVING` · `INSPECTION` | 입고 직후, **검수 전** | 검수하지 않은 물건이 고객에게 간다 |
| `IN_TRANSIT` | 센터 간 이관 중, **트럭 위** | 창고에 없는 물건을 집어 올린다 |

### 이것이 가장 중요한 지점 — 이미 도달 가능한 버그였다

처음에는 "시드에 대기 재고가 없으니 실제로는 일어나지 않는 잠재 버그" 라고
생각했습니다. 그런데 확인해 보니 아니었습니다.

**입고 등록 화면의 구역 선택 목록에 입고 대기 구역이 그대로 들어 있었습니다.**

```
사용자가 입고 등록 → 구역으로 '입고 대기(R-01)' 선택
      → 그 재고가 그대로 FEFO 출고 후보에 잡힌다
      → 주문 출고 실행 시 검수 전 재고가 차감된다
```

**사용자가 UI 만 정상적으로 조작해도 도달하는 경로**였습니다.
시드 데이터가 우연히 그 구역을 비워 두고 있어서 아무도 밟지 않았을 뿐입니다.

여기서 배운 것이 이번 프로젝트 전체에서 가장 값진 것이었습니다.

> **시드 데이터가 버그를 숨기고 있었다.**
> 정합성 검증은 모두 통과했습니다. 규칙을 어긴 데이터는 하나도 없었습니다.
> 다만 **버그가 발동하는 상태에 데이터가 도달한 적이 없었을** 뿐입니다.
> "테스트가 다 통과한다" 와 "버그가 없다" 는 다른 문장입니다.

### 해결 — 쿼리 단에서 막았다

출고 가능한 구역을 **`STORAGE`(보관) 과 `SHIPPING`(출고 대기) 둘로 한정**했습니다.

```java
and b.binPurpose in (com.feedflow.domain.BinPurpose.STORAGE,
                     com.feedflow.domain.BinPurpose.SHIPPING)
```

`SHIPPING` 을 포함시킨 것은 의도적입니다. 출고 대기 구역은
**이미 피킹해서 내보내려고 모아 둔 물량**입니다. 이걸 막으면 정상적인
출고 작업 흐름이 끊깁니다. 반대로 `RECEIVING` · `INSPECTION` 은 아직
품질 판정이 끝나지 않았고, `IN_TRANSIT` 은 애초에 창고 안에 없습니다.

**서비스 계층이 아니라 쿼리에서 막은 이유**는, 후보를 다 가져온 뒤 자바에서
걸러 내면 걸러진 만큼을 다시 채우기 위해 조회를 반복해야 하고
정렬(FEFO) 순서까지 흐트러지기 때문입니다. 애초에 후보에 넣지 않는 것이 맞습니다.

### 한 곳만 고치면 더 이상한 버그가 된다

같은 조건을 쓰는 쿼리가 하나 더 있었습니다. 주문 출고 **미리보기**용
일괄 조회 `findAllocatableByProductIds` 입니다.

한쪽만 고치면 이렇게 됩니다.

```
미리보기 : "출고 가능합니다"  (대기 구역 재고까지 세었으니까)
실행     : "재고가 부족합니다" (실제 차감은 보관 구역만 보니까)
```

**미리보기에서 보이던 재고가 실행 시점에 사라지는** 버그입니다.
원래 버그보다 더 설명하기 어렵습니다. 두 쿼리를 함께 고치고,
서로의 JavaDoc 에 **"조건이 같아야 한다"** 를 명시했습니다.

### 거부한 안 — `BinPurpose` 에 '출고 가능' 축을 추가하기

`BinPurpose` 는 이미 세 개의 축(`countedInCapacity` · `physicalSpace` ·
`systemManaged`)을 가진 enum 입니다. 네 번째 축으로 `shippable` 을 추가하면
"어떤 구역에서 출고할 수 있는가" 가 enum 한 곳에 모입니다. 자연스러워 보였습니다.

**그런데 JPQL 은 enum 의 메서드를 호출할 수 없습니다.**
`where b.binPurpose.shippable = true` 같은 것은 쓸 수 없습니다.
결국 쿼리에는 용도를 다시 열거해야 하고, 그러면 **진실이 두 곳으로 갈라집니다.**
enum 에 축을 추가한 사람은 그것만 바꾸고 쿼리는 그대로 두게 됩니다.
있는 것보다 나쁩니다. 그래서 **JPQL 을 유일한 출처로 두고 JavaDoc 으로 설명**했습니다.

### 검증 — JPQL 안에만 있는 조건은 단위 테스트로 잡히지 않는다

이 조건은 자바 코드가 아니라 **문자열 안**에 있습니다.
Mockito 로 리포지토리를 스텁하면 어떤 조건을 걸었든 테스트는 통과합니다.
그래서 `@DataJpaTest` 로 실제 H2 를 띄우는 테스트를 새로 만들었습니다.

**`AllocatableStockRepositoryTest`** — 다섯 용도(`STORAGE` · `RECEIVING` ·
`INSPECTION` · `SHIPPING` · `IN_TRANSIT`)의 구역을 모두 만들고 같은 로트를 넣어

- 보관 · 출고 대기 재고만 후보로 나오는지
- 단건 조회와 미리보기용 일괄 조회의 결과가 **같은지**
- 만료 로트 · 사용 중지 구역 제외가 함께 지켜지는지

를 검증합니다. 결과는 **품목 전체 재고 720 · 출고 가능 600.**
이 120 의 차이가 곧 "막아 낸 양" 입니다.

### 파생 — 안내 문구가 여섯 곳에 있었고, 전부 틀렸다

조건을 두 가지에서 네 가지로 늘렸으니 안내 문구도 맞춰야 합니다.
그런데 "출고 대상에서 제외됩니다" 를 설명하는 곳을 찾아보니 **여섯 군데**였고,
전부 예전 두 가지(만료 로트 · 사용 중지 구역)만 말하고 있었습니다.

```
예외 메시지 · 직접 출고 화면(입력 도움말 · 결과 안내) ·
주문 출고 미리보기 · 출고 API 응답 · 입고 등록 화면
```

여섯 곳을 네 가지로 통일했습니다.

```
유통기한 경과 로트, 사용 중지 구역, 입고 대기 · 검수 구역(검수 전),
운송 중 재고는 출고 대상에서 제외되므로 품목 목록의 전체 재고보다 적을 수 있습니다.
입고 대기 구역의 재고는 구역 간 이동으로 보관 구역에 넣어야 출고할 수 있습니다.
```

마지막 줄을 넣은 것이 핵심입니다. **막기만 하고 방법을 알려 주지 않으면
사용자는 시스템이 고장 났다고 판단합니다.** 재고가 눈에 보이는데
출고가 안 되면 원인이 아니라 해결책을 알아야 합니다.

한 걸음 더 나가서, **입고 등록 직후에 미리 경고**하도록 했습니다.
출고를 시도할 때 알려 주면 이미 늦습니다.

```java
// InboundResultDto
public boolean isNotShippableBin() { ... }
```

입고한 구역이 보관 · 출고 대기가 아니면 결과 화면에서 바로
"이 재고는 검수 후 보관 구역으로 옮겨야 출고할 수 있습니다" 를 띄웁니다.

### 실사용 검증

로컬에서 실제로 돌려 확인했습니다.

```
① 전체 재고 720 인 품목에 601 출고 요청
   → 차단. "출고 가능 재고가 1개 부족합니다. (요청 601 / 가능 600)"
     + 네 가지 제외 사유 + 해결 방법 안내

② 대기 구역 120 을 '구역 간 이동' 으로 보관 구역에 넣음
   → 720 / 720 출고 가능
```

막기만 한 것이 아니라 **막힌 재고를 정상 경로로 풀 수 있다**는 것까지
확인한 뒤 마무리했습니다.

### 이 사건에서 남은 것

1. **UI 품질 점검이 도메인 버그를 잡아냈다.** "이 문구가 왜 안 보이지" 라는
   사소한 질문이 시작이었습니다. 화면을 실제로 들여다보는 일은 낭비가 아닙니다.
2. **재고가 있다 ≠ 출고할 수 있다.** 수량은 하나의 숫자지만 **상태**가 있습니다.
   WMS 에서 이 구분을 놓치면 장부와 실물이 갈라집니다.
3. **같은 규칙을 쓰는 곳을 먼저 다 찾는다.** 쿼리 2곳 · 안내 문구 6곳.
   한 곳만 고치면 원래 버그보다 설명하기 어려운 버그가 됩니다.
4. **JPQL 안의 조건은 `@DataJpaTest` 로만 검증된다.** 모킹된 테스트는
   쿼리 문자열에 대해 아무것도 말해 주지 않습니다.

## 2. 라벨이 계산을 반박하고 있었다 — 적재율의 분자와 분모

대시보드 카드가 이렇게 나왔습니다. **숫자는 전부 정확했습니다.**

```
전국 보관 수량   4,836 / 수용 9,600 포대
전국 적재율      48%
```

4,836 ÷ 9,600 은 50% 입니다. 그런데 48% 로 표시됩니다.
버그가 아닙니다. 적재율의 분자는 전체 재고가 아니라 **보관 구역 재고 4,570**
이었습니다(4,570 ÷ 9,600 = 48%). 계산은 맞았고, **틀린 것은 라벨**이었습니다.
'보관' 이라는 단어를 전체 재고에 붙여 놓아서, 바로 아래 줄의 계산과
모순되게 보였습니다.

심사관이 "왜 50% 가 아닌가" 라고 물으면 화면만으로는 답할 수 없습니다.
**설명이 필요한 화면은 이미 잘못된 화면입니다.**

그런데 라벨을 고치려고 파고들자 그 아래에 진짜 버그가 있었습니다.
원래 적재율은 이랬습니다.

```
적재율 = 센터의 전체 재고 / 보관 구역 수용량
         └ 대기 · 운송 중 · 사용 중지 포함   └ 활성 보관 구역만
```

**분자와 분모의 기준이 달랐습니다.** 대기 구역에 물건이 들어오는 순간
적재율이 부풀고, 심하면 100% 를 넘습니다. 같은 센터가 2D 도면에서는 60%,
대시보드에서는 90% 로 보입니다. 도면은 대기분을 빼고 계산하기 때문입니다.

가장 뜨끔했던 것은, 분모를 구하는 `findStorageCapacityByCenter()` 의 주석에
제가 이미 이렇게 써 두었다는 점입니다.

> 기준이 도면과 다르면 같은 센터의 적재율이 화면마다 다르게 보인다.

**규칙을 알고 있었고, 문서로 적어 두었고, 분모만 지켰습니다.**
아는 것과 지키는 것은 다릅니다. 그래서 이번에는 주석을 더 쓰는 대신
**구조로 막기로** 했습니다.

- 전체 재고(`findStockByCenter`) 와 보관 구역 재고(`findStorageStockByCenter`) 를
  분리해 **분포 · 비중에는 전체, 적재율 · 여유 · 뱃지에는 보관 구역**만 쓴다
- 두 값의 차이는 숨기지 않고 `waitingQuantity` 로 표시한다
  (그러지 않으면 "재고 900 인데 적재율 60%" 를 설명할 수 없다)
- 적재율 계산을 `usageRate(storageQuantity, storageCapacity)` **헬퍼 하나로 모은다**
- 라벨을 `전국 보관 수량` → `전국 재고 수량` 으로 바꾸고,
  부제에 `보관 4,510 / 수용 9,600` 을 넣어 **적재율의 분자를 그 자리에 노출**한다

마지막으로 변수명을 고쳤습니다. 문제의 코드에서 두 값의 이름은
**`s` 와 `ss`** 였습니다. 한 글자 차이입니다.
`totalStock` / `storageStock` 으로 바꿨습니다.
**이번 프로젝트에서 가장 오래 붙잡은 버그의 원인은 이름이었습니다.**

## 3. 운송 중인 재고는 어디에 속하는가 — `IN_TRANSIT`

단일 창고를 전국 5거점으로 확장하면서 가장 오래 고민한 질문입니다.

기존에 구역 간 이동은 `MOVE` 한 건으로 처리했습니다. 총량이 변하지 않으니
`sign = 0` 입니다. 그런데 **센터가 다르면 출발 센터의 재고는 실제로 줄어듭니다.**
`MOVE` 로 처리하면 센터별 재고가 영구히 어긋납니다.

더 어려운 것은 그 다음입니다. 출발 센터에서 빼고 도착 센터에 넣기 전,
**그 재고는 어디에 있는가?** 어디에도 두지 않으면 프로젝트 전체의 기준선인
재고 3계층 불변식이 깨집니다.

```
Product.totalStock = Σ ProductLot.lotQuantity = Σ Inventory.quantity
```

가장 쉬운 길은 **정합성 점검에 "운송 중은 예외" 를 넣는 것**이었습니다.
이 안을 거부한 이유가 이 프로젝트에서 제가 가장 지키고 싶었던 원칙입니다.

> **안전 장치를 추가하려고 기존 안전 장치를 무디게 하는 거래는 하지 않는다.**
> 점검 로직에 예외를 하나 넣으면, 그 예외가 **진짜 어긋남까지 가려 버립니다.**
> 그 뒤로는 정합성 점검 화면의 "이상 없음" 을 신뢰할 수 없게 됩니다.

채택한 안은 **출발 센터 소속 `IN_TRANSIT` 가상 구역을 경유**하는 것입니다.
운송 중 재고도 어딘가의 `Inventory` 행으로 존재하므로 불변식이 계속 성립하고,
점검 로직에 예외가 하나도 들어가지 않습니다.

가상 구역을 **출발 센터 소속**으로 둔 것은, 운송 중 재고가 아직 출발 센터의
책임 아래 있고 분실 · 파손 시 책임 소재도 그쪽이기 때문입니다.

여기서 **감출수록 관찰할 수 없어진다**는 문제를 하나 더 만났습니다.
가상 구역은 사람이 고를 수 없어야 하니 화면에서 숨기는 것이 맞습니다.
그런데 전부 숨기면 이관이 중간에 깨져도 알아챌 방법이 없습니다.
이관은 한 트랜잭션에서 끝나므로 **잔량은 항상 0 이어야 하고**,
정합성 점검 화면에 잔류 재고 항목을 따로 두어 **0 이 아닐 때만 드러나게** 했습니다.

이 작업의 부수 효과로 `BinPurpose` 의 축을 셋으로 나눴습니다.
"대기 구역" 과 "운송 중" 은 둘 다 적재율에서 빠지지만 성격이 전혀 다릅니다.
대기 구역은 **창고 안의 실제 바닥**이라 한도가 있고 도면에 그려야 하고,
운송 중은 물리적 공간이 아닙니다. 하나의 boolean 으로는 표현할 수 없었습니다.

적재 한도 문제도 `maxCapacity` 를 큰 수로 잡아 우회하지 않고
**검증 자체를 건너뛰게** 했습니다. 임의의 큰 수는 언젠가 넘고,
넘었을 때 왜 막혔는지 아무도 알 수 없습니다.

## 4. 시드 데이터도 '보여줄 수 있는가' 로 검증한다

정합성 5규칙을 다 지켜도 **기능을 보여주지 못하는 데이터**가 만들어집니다.
1번 사건이 정확히 그 사례였고, 그 뒤로 검증 기준을 하나 더 만들었습니다.

| 증상 | 규칙 위반 | 화면에서 보이는 것 |
|---|---|---|
| 최근 7일 입고 +1,660 / 출고 −10 | 없음 | "물류가 멈춘 창고" |
| 활성 보관 구역인데 재고 0 | 없음 | 2D 도면의 영구 빈 칸 |
| 시드부터 포화(90%↑)인 구역 6곳 | 없음 | 포화 경보가 의미를 잃고, 이동을 시연할 여유도 없다 |
| 대기 구역 재고 0 | 없음 | `+ 대기 구역 N포대 별도` 가 한 번도 렌더링되지 않는다 |

출고 이력을 보강하는 데 걸림돌이 하나 있었습니다. 배송 완료 주문에
`OUTBOUND` 이력을 붙이면 **최종 재고가 줄어들어** 어렵게 맞춘 구역별 배치가
무너집니다. 그래서 짝이 되는 `INBOUND` 를 **25일 이상 더 오래된 날짜**로
함께 넣었습니다.

```
입고 +q (25일 이상 과거)  +  출고 −q (주문일)  =  0
```

최근 7일 집계에는 출고만 들어오고, 최종 재고는 그대로입니다.
기간 통계는 살아 움직이는데 재고 배치는 흔들리지 않습니다.

이력 누적 = 최종 재고를 로트 단위뿐 아니라 **`로트 × 구역` 단위까지** 맞췄습니다.
`MOVE` · `TRANSFER` 의 출발 구역에 그 로트가 입고된 기록이 없으면
로트 총량은 맞아도 구역별로 어긋나고, 이력 추적 화면이 정합성 경고를 띄웁니다.

## 5. 빌드할 수 없는 환경에서 어떻게 신뢰를 확보했는가

개발 샌드박스는 외부 네트워크가 차단(`INTEGRATIONS_ONLY`)되어
**Gradle 의존성을 내려받을 수 없었습니다.** 즉 컴파일도, 테스트 실행도
샌드박스 안에서는 불가능했습니다. 로컬 실행은 사이클이 길기 때문에
"일단 밀어 넣고 빌드가 깨지면 고친다" 는 방식은 쓸 수 없었습니다.

그래서 **정적 검사기 14종**을 직접 만들어 컴파일러가 해 줄 일 중
자동화할 수 있는 것을 대신했습니다.

```
import 누락/미사용 · 괄호 균형 · enum switch 망라성 ·
JPQL select new 인자 수 ↔ record 컴포넌트 수 ·
템플릿 ${} ↔ 컨트롤러 모델 키 · 템플릿 프로퍼티 ↔ DTO 게터 ·
JS 가 읽는 JSON 필드 ↔ record 컴포넌트 · node --check ·
Mockito STRICT_STUBS 안전성 · 같은 파일 내 메서드 호출 인자 수 …
```

가장 효과가 컸던 것은 **`select new` 인자 수 ↔ record 컴포넌트 수** 대조입니다.
JPQL 은 문자열이라 컴포넌트를 하나 추가해도 컴파일이 통과하고,
**애플리케이션이 뜨는 순간에야** 터집니다.

그리고 검사기를 하나 만들 때마다 **일부러 오류를 심어 실제로 검출되는지
확인한 뒤 원복**했습니다. 검사기가 조용히 통과만 하고 있는 것과
정말로 잡을 수 있는 것은 전혀 다릅니다. 검증되지 않은 검사기는
**틀린 안심**을 줍니다.

최종적으로 로컬 `gradlew build` 는 **BUILD SUCCESSFUL**,
테스트 **242개 / 18개 클래스** 전부 통과했습니다.

## 6. 검사기가 503건을 잡았는데 전부 오탐이었다

팀원의 고객 농장 모듈을 통합할 때 **빌드를 돌릴 수 없는 상황**이었습니다. 샌드박스는
네트워크가 막혀 있고 로컬 확인도 어려운 상태였습니다. 파일 13개를 새로 넣는데
컴파일 검증이 없다는 것은, 오류가 있어도 **아무도 발견할 방법이 없다**는 뜻입니다.

그래서 컴파일러 역할을 일부 대신하는 검사기를 만들었습니다. 타입 해석, Lombok 빌더
체인 ↔ 실제 필드, `new Record(...)` 인자 수, enum 상수 참조, JPQL `:param` ↔ `@Param`,
Thymeleaf 프로퍼티 ↔ DTO 게터를 대조하는 것이었습니다.

첫 실행 결과는 **실패 503건**이었습니다.

```
[빌더] FarmCustomerDto.java : FarmCustomerDto.builder().getFarmCode() —
       FarmCustomerDto 에 getFarmCode 필드가 없다
```

맞는 말처럼 보입니다. `FarmCustomerDto` 에 `getFarmCode` 라는 필드는 없으니까요.
그런데 실제 코드는 이렇습니다.

```java
FarmCustomerDto.builder()
        .farmCode(farm.getFarmCode())   // ← 빌더 메서드는 farmCode
        .build();
```

**빌더 체인을 파싱할 때 괄호 깊이를 세지 않아서**, 인자 안에 있는 `getFarmCode(` 까지
빌더 메서드로 읽은 것입니다. 503건 전부 이 한 가지 버그였습니다.

### 이 순간이 가장 위험했다

만약 503건을 그대로 믿었다면 **정상 코드를 대규모로 고쳤을 것**입니다. 빌드를 돌릴 수
없으니 고친 결과가 맞는지도 확인할 수 없고, 오류는 오류를 부릅니다.

고친 뒤 남은 2건도 오탐이었습니다. `BinLoadStatus.FULL_THRESHOLD` 를 "없는 enum 상수"
라고 보고했는데, 그것은 enum 안에 선언된 `public static final int` 였습니다. 필드를
수집할 때 `private` 만 봤던 것입니다.

**503 → 2 → 0.** 두 번 모두 코드가 아니라 검사기가 틀렸습니다.

### 그래서 검사기에도 같은 원칙을 적용했다

이 프로젝트에서 검사기를 만들 때마다 **일부러 오류를 심어 검출되는지 확인한 뒤
원복**했습니다. 이번에도 네 가지를 심었습니다.

| 심은 오류 | 검출 |
|---|---|
| 빌더에 없는 필드 `.nonExistentField("x")` | ✅ |
| 템플릿이 `${f.noSuchProperty}` 참조 | ✅ |
| `@Param("animalTypeX")` 로 이름 불일치 | ✅ 양방향(쿼리에 없는 파라미터 / 안 쓰는 `@Param`) |
| `CustomerStatus.RUNNING` (없는 상수) | ✅ |

이걸 하지 않았다면 "통과했다" 는 출력이 무엇을 뜻하는지 알 수 없었습니다.
**검증되지 않은 검사기는 틀린 안심을 줍니다.**

### 그 뒤로도 세 번 더 틀렸다

수요 계획 기능을 추가하면서 같은 검사기가 또 오탐과 미탐을 냈습니다.

| 회차 | 증상 | 원인 |
|---|---|---|
| 3 | `private record CoverageKey` 를 "import 안 했다" 8건 | **중첩 타입을 수집하지 못했다.** 선언 정규식이 `private` 를 허용하지 않았다 |
| 4 | `LabelType.PRODUCT` 를 "없는 상수" | `enum LabelType { LOT, PRODUCT }` 처럼 **마지막 상수가 본문 끝**에 오면 경계 문자가 없어 놓쳤다 |
| 5 | **아무것도 보고하지 않았다** | `${plan.x}` 만 보고 `${#numbers.formatInteger(plan.x, 1, 'COMMA')}` 안은 검사하지 않았다 |

**5번이 가장 위험했습니다.** 오탐은 시끄러워서 확인하게 되지만, 미탐은 조용합니다.
템플릿의 숫자 표시는 대부분 `#numbers.formatInteger(...)` 로 감싸므로, 사실상
**프로퍼티 참조 대부분이 검사 밖에 있었는데 "통과" 라고 출력되고 있었습니다.**

고친 뒤 일부러 틀린 프로퍼티를 심어 보니 그때서야 잡혔습니다. 이걸 확인하지 않았다면
검사기는 계속 통과만 하고 있었을 것입니다.

### 검사기가 진짜 문제를 잡은 것도 있다

`DemandPlanRepositoryTest` 에서 `org.assertj.core.groups.Tuple.tuple(...)` 처럼
완전 정규화된 이름을 썼습니다. 컴파일은 되지만 읽기 나쁩니다.
검사기가 이걸 잡아 줘서 `import static org.assertj.core.api.Assertions.tuple;` 로
정리했습니다. 검사기에도 FQN 을 인식하는 규칙을 추가했습니다.

**다섯 번 중 네 번은 검사기가 틀렸고, 한 번은 코드가 틀렸습니다.**

### 여섯 번째 · 일곱 번째 — 검사기가 자기 눈을 가리고 있었다

불량 관리 기능을 넣을 때 두 번 더 고쳤습니다. 이번 것은 성격이 달랐습니다.

| 회차 | 증상 | 원인 |
|---|---|---|
| 6 | `NumberFormatException` 을 "import 안 했다" 4건 | `java.lang` 허용 목록에 표준 예외가 빠져 있었다 |
| 7 | 실재하는 리포지토리 메서드를 "그런 메서드가 없다" 5건 | **`@Query` 텍스트 블록의 JPQL 이 메서드 수집을 오염시켰다** |

7번의 원인을 찾는 데 시간이 걸렸습니다. 인터페이스 메서드를 찾는 정규식이
`네 칸 들여쓰기 + 반환타입 + 이름(...);` 패턴을 보는데, 바로 위 `@Query` 텍스트 블록 안의

```
select new com.feedflow.admin.dto.DefectStatRow(
           cast(d.defectType as string), count(d), sum(d.quantity))
```

이 부분이 같은 패턴에 걸렸습니다. `select new` 를 반환 타입으로, `DefectStatRow(` 를
메서드 이름으로 읽고, 닫는 `);` 를 찾아 **아래 실제 선언까지 삼켰습니다.**
그래서 `findStatsByType` 이라는 이름이 수집되지 않았고, 그것을 호출하는 서비스가
"없는 메서드를 부른다" 고 잡혔습니다.

고친 방법은 단순합니다. 수집 단계에서 **문자열 · 텍스트 블록 · 주석을 먼저 걷어냅니다.**
타입 해석 단계에서는 이미 그렇게 하고 있었는데, 메서드 수집 단계에서만 빠뜨렸습니다.
줄바꿈 개수는 유지해야 합니다 — 들여쓰기로 인터페이스 메서드를 찾는 규칙이 있어서
줄이 붙으면 그쪽이 깨집니다.

**7번은 그냥 오탐이 아니라 검사기가 새로 추가한 검사를 스스로 무력화한 사례입니다.**
이번에 추가한 검사가 바로 그 "주입 필드를 통한 리포지토리 메서드 호출 존재 여부" 였습니다.
그전까지는 `defectRecordRepository.countOpen()` 을 `countOpenXX()` 로 잘못 써도
아무도 알려주지 않았습니다 — **미탐이었습니다.** 검사를 추가한 첫 실행에서
오탐 5건이 함께 나왔고, 오탐을 없애자 심어 둔 오타 1건만 정확히 남았습니다.

Lombok 접근자도 재현해야 했습니다. `stage.getDescription()` 은 소스에 없는 메서드입니다
(`@Getter` 가 만듭니다). 이걸 모르면 정상 호출이 전부 오탐으로 잡힙니다.
필드 타입까지 수집해 `getXxx` · `boolean` 이면 `isXxx` · `@Setter` 면 `setXxx` 를
만들어 두는 방식으로 처리했습니다.

### 시드 검사기는 자기가 죽는 방식이 나빴다

불량 시드 검사기를 만들고 오류 5종을 심어 확인하는데, 첫 번째(없는 `lotId`)에서
**스택 트레이스만 남고 끝났습니다.** FK 오류를 기록한 뒤에도 검사를 계속해서,
없는 키를 뒤지다 `KeyError` 로 죽은 것입니다.

검사기가 죽으면 "무엇이 틀렸는지" 대신 파이썬 예외를 읽게 됩니다. 참조 무결성이
깨진 상태에서 나머지를 검사하는 것은 의미도 없습니다. FK 검사 단계에서 실패가 있으면
그 자리에서 정리해 출력하고 종료하도록 바꿨습니다.

**검사기를 만들 때는 통과하는 경우만 확인하기 쉽습니다.** 실패할 때 어떻게 실패하는지도
봐야 합니다.

### 남은 것

검사기는 저장소의 [`tools/`](../tools/) 에 넣어 두었습니다. 다만 한계를 문서에
분명히 적었습니다 — 제네릭 타입 불일치, 오버로딩 해석, 상속 관계는 보지 못하고,
로직이 맞는지는 알 수 없습니다. **`gradlew build` 를 대체하지 못합니다.**

검사기는 의심할 지점을 좁혀 주는 도구이고, 판단은 사람이 합니다. 이번에 그 판단을
하지 않았다면 검사기가 코드를 망가뜨렸을 것입니다.

> 실제로 로컬 빌드가 가능해진 뒤 `gradlew build` 를 돌렸더니 **`BUILD SUCCESSFUL`**
> 이었습니다. 검사기가 잡아낸 것들이 실제 컴파일 오류였는지는 알 수 없지만,
> 적어도 검사기를 통과한 코드가 컴파일된다는 것은 한 번 확인됐습니다.

### 그리고 검사기가 잡을 수 없는 것에서 실제로 실패했다

수요 계획 기능을 넣고 빌드했더니 **테스트 295개 중 1개가 실패**했습니다.
정적 검사 5종은 모두 통과한 상태였습니다.

```
DemandPlanServiceTest.totalsAreSumOfAnimals
  animalsNeedingAction : 기대 1 인데 실제 2
```

테스트 데이터를 이렇게 짰습니다.

| | 수요 | 재고 | 비율 | 판정 |
|---|---|---|---|---|
| 센터1 소 | 720 | 500 | 69% | SHORTAGE → 조치 필요 |
| 센터1 가금 | 200 | 300 | 150% | ADEQUATE |
| 센터2 돼지 | 900 | 1,000 | **111%** | **TIGHT → 조치 필요** |

"재고가 수요보다 많으니 괜찮겠지" 하고 조치 대상을 1건으로 적었는데,
**111% 는 제가 직접 만든 `TIGHT`(100~120%) 구간**이었습니다. 딱 한 달치라
발주가 늦으면 바로 부족해지므로 조치 대상으로 세도록 만들어 둔 것인데,
테스트를 쓸 때 그 규칙을 제가 잊었습니다.

**프로덕션 코드는 정상이었고 테스트가 틀렸습니다.** 이건 검사기가 잡을 수 없습니다.
타입도 참조도 맞고, 문법도 맞습니다. 틀린 것은 **숫자**입니다.
`tools/README.md` 에 "로직이 맞는지는 알 수 없다" 고 적어 둔 그 한계에
정확히 해당하는 실패였습니다.

그래서 [`tools/verify_test_expectations.py`](../tools/verify_test_expectations.py) 를
만들었습니다. `CoverageStatus` 와 `AnimalCoverageDto` 의 계산을 파이썬으로 옮겨,
테스트에 적어 둔 기대값을 재계산해 대조합니다. 빌드 사이클이 느린 환경에서
숫자 오류 하나로 51초를 쓰는 것보다 낫습니다.

이 검증기도 오류를 심어 확인했습니다. **방금 실패한 것과 똑같은 실수(2를 1로)를
되돌려 심으니 정확히 그 두 줄을 짚어냈습니다.**

교훈은 검사기를 하나 더 만든 것이 아닙니다. **경계값을 정해 놓고 테스트를 쓸 때
그 경계를 다시 확인하지 않았다는 것**입니다. 111% 가 어느 구간인지는 제가 30분 전에
직접 정한 것이었습니다.

## 7. 팀원 모듈을 옮기면서 절반을 버렸다 — 불량 관리

팀원 저장소에 `Manufacturer`(제조사)와 `DefectRecord`(불량 기록)가 있었습니다.
그대로 복사하면 30분이면 끝나는 일이었습니다. 그렇게 하지 않았습니다.

### 왜 필요했나

우리 시스템은 검수 전 재고가 출고되지 않도록 막고 있었습니다. 그런데 **막은 다음**에
무엇을 하는지가 없었습니다. 검수에서 불량을 발견하면 그 재고는 검수 구역에 남아 있고,
누구도 그것이 왜 거기 있는지 알 수 없습니다. 제조사별로 반복되는지, 어느 단계에서
잡히는지, 격리한 채 며칠이 지났는지 — 물어볼 데이터가 없었습니다.

### 겹치는 enum 을 합치지 않은 이유

우리에게 `DisposalReason`(폐기 사유)이 있었고 팀원에게 `DefectType`(불량 유형)이
있었습니다. 값이 4개 겹칩니다 — 파손, 오염, 침수, 유통기한 경과.

합치는 것이 중복 제거로 보입니다. 합치지 않았습니다. **묻는 것이 다릅니다.**

| | 묻는 것 | 값의 예 |
|---|---|---|
| `DefectType` | 무엇이 잘못됐나 | 규격 미달, 이물 혼입 |
| `DisposalReason` | 왜 버리나 | 재고 실사 손실, 샘플 사용 |

불량이 반드시 폐기로 가지 않습니다(재작업 · 특채). 반대로 폐기 사유에는 불량과
무관한 값이 있습니다. 합치면 **"재고 실사 손실" 이라는 불량 유형**이 생깁니다.
대신 `DefectType.toDisposalReason()` 매핑을 두어, 폐기로 처리할 때 사유를 이어받게 했습니다.

### 팀원의 값을 그대로 쓰지 않았다

팀원의 `OccurrenceStage` 는 5개였습니다. 우리는 4개로 바꿨습니다.

- **생산 단계 제외** — 우리는 유통만 합니다. 만들지 않는 것의 불량 단계를 둘 수 없습니다.
- **고객 반품 제외** — 반품 절차를 의도적으로 만들지 않았습니다. **없는 기능의 선택지를
  화면에 두면, 담당자는 그것을 고르고 다음 화면이 없다는 것을 발견합니다.**
- **센터 간 이관 추가** — 우리에게는 `IN_TRANSIT` 구간이 있습니다. 운송 중 파손은
  실제로 일어나고, 이때는 어느 구역에서 났다고 말할 수 없습니다(그래서 `binId` 가 nullable).

결과적으로 4단계가 우리 `BinPurpose` 와 1:1 로 대응합니다. 구역만 고르면 단계가
정해지므로 담당자에게 같은 것을 두 번 묻지 않습니다.

### 가장 중요한 결정 — 이 기능은 재고를 바꾸지 않는다

불량을 폐기로 처리하면 재고가 줄어야 할 것 같습니다. 그렇게 하지 않았습니다.

재고를 줄이는 코드가 두 곳에 있으면 언젠가 한쪽만 고칩니다. 그때 **재고는 줄었는데
이력이 없거나, 이력은 있는데 재고가 그대로인 상태**가 생기고, 어느 쪽이 맞는지
알 수 없습니다. 이 프로젝트에서 이미 같은 종류의 문제(적재율의 분모가 두 곳에서
다르게 계산되던 일)를 겪었습니다.

그래서 처리 결과에 **다음에 할 일**을 문장으로 붙였습니다.

```
DF-2607-004 처리 완료 — 공급업체 반품 ·
재고 폐기 화면에서 해당 수량을 차감해야 장부와 실물이 맞습니다. 제조사 연락처를 확인하세요.
```

사람이 한 번 더 클릭하는 대가로, 재고 숫자의 출처를 한 곳으로 유지합니다.
화면에는 '재고 차감 대기' 카드를 두어 **아직 차감하지 않은 건이 몇 건인지** 보이게 했습니다.

### 상태를 되돌릴 수 없게 만들었다

`RESOLVED` 에서 `QUARANTINED` 로 돌아가는 전이를 막았습니다. 편의성만 보면 허용하는 게 낫습니다.

같은 로트에서 불량이 다시 나왔을 때 기존 건을 되살려 쓰면, **"이 로트에서 몇 번
나왔는가" 를 셀 수 없습니다.** 그것이 공급업체 평가의 근거인데 한 건에 덮어써서
뭉개집니다. 그래서 되돌리려 하면 이렇게 안내합니다.

> 이미 처리된 건은 되돌릴 수 없습니다. 같은 로트에서 불량이 다시 나왔다면 새 건으로 등록하세요.

### 등록 권한을 사원까지 열었다

처리 완료는 책임자 전용으로 뒀습니다(반품은 거래처 문제, 폐기는 비용, 되돌릴 수 없음).
**등록은 사원도 할 수 있게 했습니다.** 불량은 현장에서 발견되고, 책임자를 기다려야
기록할 수 있으면 담당자는 기록을 아예 남기지 않는 쪽을 택합니다. 그러면 이 기능이
답하려던 질문이 데이터 부족으로 무의미해집니다.

### 제조사 미등록을 숨기지 않았다

기존 품목 13개에는 제조사 정보가 없었습니다. `manufacturerId` 를 필수로 두면
기존 데이터를 넣을 방법이 없습니다. nullable 로 두고, 시드에서도 **한 품목은 일부러
비워 뒀습니다.**

제조사별 집계에서 이것을 제외하면 합계가 전체와 맞지 않아 설명할 수 없고, 등록이
필요하다는 사실도 드러나지 않습니다. `coalesce(m.name, '미등록')` 으로 묶어
함께 세고, 화면에 이렇게 알립니다.

> 제조사가 등록되지 않은 품목의 불량이 1건 있습니다. 반품을 검토하려 해도 **대상을
> 특정할 수 없습니다** — 품목 정보에 제조사를 등록해 두세요.

### `left join` 하나가 조용히 데이터를 지운다

목록 쿼리에서 제조사를 `join fetch` 로 쓰면, **제조사가 없는 품목의 불량이 통째로
사라집니다.** 에러가 아니라 결과가 조용히 줄어드는 방식으로 틀립니다.
화면만 봐서는 알 수 없습니다.

`DefectRecordRepositoryTest` 의 첫 테스트가 이것입니다. 제조사 있는 품목과 없는 품목의
불량을 각각 넣고 2건이 나오는지 확인합니다.

### 목록 정렬도 결정이었다

최신순이 자연스러워 보입니다. **미처리 우선 + 오래된 것부터**로 했습니다.
격리한 재고는 출고되지 않으면서 자리를 차지합니다. 최신순으로 두면 가장 오래
방치된 건이 목록 끝으로 밀려 영원히 보이지 않습니다.

추가로 7일이 지난 미처리 건은 목록 위에 별도 경고로 띄우고, 행 배경도 바꿉니다.
이 경고는 **필터와 무관하게** 항상 나옵니다 — 상태 필터를 '처리 완료' 로 둔 상태에서도
방치된 재고는 보여야 합니다.

## 8. 프로세스 실수 — 같은 사고를 두 번 냈다

기술 회고만 남기면 정직하지 않으므로, 제가 두 번 반복한 실수도 적습니다.

작업을 단계별 브랜치로 쪼개면서 PR 의 base 브랜치를 **아직 머지되지 않은
직전 단계 브랜치**로 잡았습니다. 그 브랜치가 먼저 머지되면 GitHub 이
알아서 재타겟해 줄 것이라고 생각했습니다.

**틀렸습니다.** 자동 재타겟은 base 브랜치가 **삭제될 때만** 일어납니다.
그 결과 PR 은 "Merged" 로 표시되는데 변경 내용이 통합 브랜치에는
**도달하지 않은** 상태가 됐습니다. 화면에 초록색 배지가 떠 있으니
문제가 있다는 신호가 어디에도 없었습니다.

더 나쁜 것은 **이 사고를 두 번 냈다는 점**입니다(PR #3 → #4, PR #11 → #12).
첫 번째에 원인을 "실수" 로 정리하고 규칙으로 만들지 않았기 때문입니다.
두 번째 뒤에야 규칙을 고정했습니다.

> **PR base 는 항상 통합 브랜치 하나로 고정한다.**
> 브랜치를 쪼개는 편의보다 "머지했다" 는 표시를 신뢰할 수 있는 것이 중요하다.

교훈은 브랜치 전략보다 그 앞에 있습니다.
**성공 표시를 성공의 증거로 믿었습니다.** 1번 사건에서 "정합성 검증 통과" 를
"버그 없음" 으로 읽었던 것과 정확히 같은 종류의 착각입니다.
그래서 머지 후에는 반드시 **통합 브랜치의 커밋 로그와 실제 파일**을
직접 확인하는 절차를 넣었습니다.

## 9. 관통하는 교훈

이번 프로젝트에서 반복적으로 만난 패턴은 하나였습니다.
**"통과했다" 는 신호를 "맞다" 로 읽는 것.**

| 착각 | 실제 |
|---|---|
| 정합성 검증 5규칙 통과 | 버그가 발동하는 데이터에 도달한 적이 없었을 뿐 |
| 화면에 숫자가 정상으로 보인다 | 시드가 우연히 분자 = 분모인 상태였을 뿐 |
| 규칙을 주석에 적어 뒀다 | 분모만 지키고 분자는 지키지 않았다 |
| 정적 검사기가 통과했다 | 검사기가 실제로 잡을 수 있는지 확인하지 않았다 |
| **검사기가 503건을 실패로 보고했다** | **검사기 자신의 버그였다. 코드는 정상이었다** |
| PR 이 Merged 로 표시된다 | 통합 브랜치에는 도달하지 않았다 |

그래서 마무리 단계의 작업들도 같은 방향으로 골랐습니다.
주석을 더 쓰는 대신 계산을 **헬퍼 하나로 모으고**(`usageRate`),
한 글자 차이 변수명을 **도메인 용어로 바꾸고**,
호출부가 사라진 코드는 "나중에 쓸지도 모른다" 는 이유로 남기지 않고 **지웠습니다.**
설명으로 지키는 규칙은 언젠가 깨지고, 구조로 지키는 규칙은 깨질 수 없습니다.
