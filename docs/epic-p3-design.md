# Phase 3a 설계 — 센터 간 재고 이관

`Epic: 전국 다중 창고 기반 물류망 확장` 의 세 번째 단계. 센터를 넘는 재고 이동을
`TRANSFER_OUT` / `TRANSFER_IN` 으로 분리하고, 그 사이 재고가 머무는 자리를 만든다.

## 해결하려는 문제

P2 에서 이력 추적에 `isCenterTransfer()` 경고를 넣었더니 실제로 걸렸다.
구역 간 이동 화면에서 제1창고 `A-01` 의 재고를 제2창고 `N-05` 로 옮길 수 있었고,
그 이력이 `MOVE` 로 기록됐다.

`MOVE` 는 **총 재고 불변**을 전제한다(`sign = 0`). 같은 센터 안에서는 맞는 말이다.
하지만 센터가 다르면 **출발 센터의 재고는 실제로 줄어든다.** `MOVE` 하나로는
"제1창고에서 나갔다" 와 "제2창고에 들어왔다" 를 구분할 수 없고, 그 둘 사이에
존재하는 **운송 중(In-Transit)** 상태를 표현할 자리도 없다.

## 검토한 세 가지 안

운송 중 재고를 어디에 둘 것인가가 핵심이었다.

| 안 | 방식 | 포기하는 것 |
|---|---|---|
| A | 운송 중 수량을 `Inventory` 밖(별도 전표 테이블)에 둔다 | **3계층 불변식**. 운송 중에는 Σ`Inventory.quantity` < `lotQuantity` 가 되어 재고 정합성 점검이 오탐한다 |
| B | 센터마다 `IN_TRANSIT` **가상 구역**을 두고 그곳에 담는다 | 가상 구역을 노출해서는 안 되는 화면이 여러 곳이다. 한 곳이라도 빠뜨리면 도면에 실체 없는 칸이 그려진다 |
| C | B + 이관 전표 엔티티(`Transfer`, `TransferItem`) + 관리 화면 | 범위. 엔티티 2개 · 화면 2개 신규 |

### 결정: B안 (P3a)

**포트폴리오 일정 대비 C안은 과하다.** 전표와 승인 흐름은 실제 운영에서 필요하지만,
이 프로젝트가 증명하려는 것은 *센터 간 이동이 재고 정합성을 깨뜨리지 않는 구조*다.
전표는 그 구조 위에 얹는 관리 레이어이므로 나중에 추가할 수 있다.

**A안은 채택하지 않았다.** P1·P2 에서 3계층 불변식을 계속 지켜왔고,
그 불변식이 `/admin/inventory/sync` 정합성 점검 화면의 근거다.
운송 중 재고를 `Inventory` 밖에 두면 점검 로직에 예외를 넣어야 하는데,
그 예외가 **진짜 어긋남을 가려버릴** 여지를 만든다. 안전 장치를 위해 안전 장치를
무디게 하는 거래는 하지 않는다.

```
Product.totalStock = Σ ProductLot.lotQuantity = Σ Inventory.quantity
                                                  ↑ 운송 중 재고도 여기 포함된다
```

## IN_TRANSIT 가상 구역

### 출발 센터 소속으로 둔다

운송 중 구역이 어느 센터에 속하는지는 답이 하나로 정해지지 않는다.

- 출발 센터 소속 → "보냈는데 아직 내 재고" 로 보인다
- 도착 센터 소속 → "아직 안 왔는데 내 재고" 로 보인다

`WarehouseBin.center` 는 `optional = false` 라 무소속으로 둘 수도 없다.
**출발 센터 소속**을 택했다. 물리적으로 아직 출발 센터의 책임 아래 있고,
분실·파손이 생겼을 때 책임 소재도 그쪽이다.

대신 **센터별 가용 재고 집계에서는 제외**한다. 출발 센터 소속이지만
"팔 수 있는 재고" 는 아니기 때문이다.

### 구역 규격

| 항목 | 값 | 이유 |
|---|---|---|
| `binCode` | `TRANSIT-{centerCode}` (예: `TRANSIT-WH1`) | 센터당 하나. 코드만 보고 성격을 알 수 있어야 한다 |
| `binPurpose` | `IN_TRANSIT` | |
| `maxCapacity` | 한도 검증 **면제** | 밀부피 있는 공간이 아니다. 트럭 대수를 여기서 셀 수는 없다 |
| `active` | `true` | 사용 중지하면 이관이 막힌다 |
| 도면 좌표 | 있으나 **도면에서 제외** | 좌표 컬럼이 `NOT NULL` 이라 값은 넣되 조회에서 뺀다 |
| 생성 시점 | 이관 시 **없으면 자동 생성** | 센터는 운영 중에 늘어난다. 센터를 만들 때마다 사람이 가상 구역을 만들게 하면 빠뜨린다 |

### 노출되어서는 안 되는 곳

가상 구역이 새어 나가면 도면에 실체 없는 칸이 그려지고, 사용자가 그 칸으로
재고를 옮길 수 있게 된다. **제외 지점을 한곳에 모아 적는다.**

| 위치 | 처리 |
|---|---|
| 2D 도면 (`findWarehouseMapRows`) | 제외 |
| 구역 선택 목록 (`findActiveBinsForSelection`) | 제외 — 이동 도착지로 고를 수 없다 |
| 구역 등록·수정 폼의 용도 select | `IN_TRANSIT` 선택 불가 (시스템이 만드는 구역이다) |
| 창고 적재율 통계 | 제외 (`countedInCapacity = false`) |
| 적재 한도 검증 | 면제 |
| 재고 현황 목록 | **노출한다.** 실재하는 재고이므로 숨기면 "재고가 사라졌다" 로 보인다 |
| 구역 관리 목록 | **노출한다.** 단 시스템 구역임을 표시한다 |

## 이관 처리 흐름

사용자에게는 기존 '구역 간 이동' 화면 하나뿐이다. 도착 구역이 다른 센터면
서비스가 알아서 이관으로 처리한다. **화면에는 즉시 완료된 것으로 보인다.**

```
같은 센터                다른 센터
─────────                ─────────
출발 구역  -N            출발 구역        -N   → TRANSFER_OUT 이력
도착 구역  +N            IN_TRANSIT(출발)  +N
                         IN_TRANSIT(출발)  -N
MOVE 이력 1건            도착 구역        +N   → TRANSFER_IN 이력
```

한 트랜잭션 안에서 두 구간을 모두 처리하므로 `IN_TRANSIT` 잔량은 **평상시 0** 이다.
그래도 경유시키는 이유는 두 가지다.

1. **이력이 두 건으로 남는다.** `TRANSFER_OUT`(제1창고 출고)과
   `TRANSFER_IN`(제2창고 입고)이 별개 이벤트로 기록되어, 이력 추적 타임라인이
   센터별 입출고를 정확히 보여준다. `MOVE` 한 건으로는 불가능했다.
2. **P3b 확장 지점이 된다.** 두 구간이 이미 분리되어 있으므로,
   나중에 실제 운송 중 상태가 필요해지면 **두 번째 구간을 즉시 호출하지 않는 것**으로
   충분하다. 구조를 다시 짜지 않는다.

### 왜 sign 이 0 이 아닌가

`TRANSFER_OUT` 은 `-1`, `TRANSFER_IN` 은 `+1` 이다. `MOVE` 처럼 0 으로 두면
"센터 관점에서 재고가 줄었다/늘었다" 를 표현할 수 없다. 두 건의 합이 0 이 되어
**전국 총량은 그대로**이고, 이것이 `lotQuantity` 를 건드리지 않는 근거다.

> 로트 잔여(`lotQuantity`)와 품목 총 재고(`totalStock`)는 이관에서 **바뀌지 않는다.**
> 전국 합계 기준이므로 센터를 옮겨도 총량은 같다. P1 에서 확정한 정책 그대로다.

## MOVE 를 센터 내부로 제한한다

`MOVE` 는 이제 **같은 센터 안에서만** 쓸 수 있다. 센터가 다르면 이관 경로로 넘어가므로,
`MOVE` 로 센터를 넘는 이력은 더 이상 생기지 않는다.
유효하지 않은 상태를 애초에 만들 수 없게 하는 것이 검증보다 낫다.

P2 에서 넣은 `TraceEventDto.isCenterTransfer()` 경고는 **그대로 둔다.**
과거에 잘못 기록된 이력(이번 개발 중 실제로 만들어진 것)을 계속 드러내야 하고,
회귀가 생기면 화면에서 즉시 보인다.

## 정합성 점검에 운송 중 잔류 항목 추가

`IN_TRANSIT` 잔량은 평상시 0 이어야 한다. 0 이 아니면 트랜잭션이 중간에 깨졌거나
P3b 로 확장된 뒤 도착 처리가 누락된 것이다. **가상 구역을 관찰 가능하게 만들어야
장식이 아니게 된다.** `/admin/inventory/sync` 에 잔류 재고 항목을 추가한다.

## 이 단계에서 하지 않는 것

| 항목 | 이유 |
|---|---|
| 이관 전표 엔티티 · 관리 화면 | 포트폴리오 범위 초과. 구조가 준비되어 있으므로 나중에 얹을 수 있다 |
| 실제 운송 중 상태(도착 처리 분리) | 두 번째 구간을 나중에 호출하는 것으로 확장 가능. 지금은 즉시 완료 |
| 운송 리드타임 · 도착 예정일 | 전표가 있어야 의미가 생긴다 |
| 이관 승인 흐름 | 같은 이유 |
| 센터별 가용 재고 뷰 | P4(대시보드)에서 다룬다 |
